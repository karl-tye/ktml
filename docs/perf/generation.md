# Generation performance

- Date: 2026-10-21
- Goal: `ktml generate` and `ktml dev`'s initial generation are faster than
  `templ generate` on a production templ application.
- Verdict: **met.** KTML generates the application in half of templ's time cold, and in
  a fifth of it warm, at every core count measured.
- Gate: `TestGenerateFilesContext_GIVENAnApplicationSizedWorkspace_WHENGeneratedColdAndWarm_THENStaysWithinTheBudget`
  in [`cmd/ktml/generation_run_test.go`](../../cmd/ktml/generation_run_test.go),
  with `BenchmarkGenerateFilesContext` beside it.

## Setup

- AMD Ryzen AI Max+ 395 (32 logical cores), 62 GB, Linux, go1.27.0.
- KTML: the converted application, with 83
  component documents and 18 Host Schemas under `internal/` (101 sources,
  34,378 lines). Generation writes 180 files: a production and a
  development variant per document, and one file per schema.
- templ: the same application before conversion, with 87 `.templ` files
  (18,923 lines), using the installed `templ` v0.3.1020 binary as its
  Makefile does.
- Times are wall-clock medians of 5 to 9 runs. Both tools ran as prebuilt
  binaries; `go tool ktml` adds about 40 ms for its build check.
  - Cold: no generated files and no `.ktml/` build state (templ: its
    `_templ.go` files deleted).
  - Warm: nothing changed since the last run.
  - One file: one appended line in one mid-sized document.
- Dev startup is `ktml dev`'s launch until it starts the backend (clearing
  `.ktml/`, the initial generation, the Explorer, and seeding the hub). It
  uses a stub backend, so the app's own startup is excluded.

compile only under `-tags ktmldev`.

## Where the time went

CPU profiles of the old `ktml generate ./internal/...`:

1. **Handwritten Go re-parsed for every reference (85% of CPU).** gogen
   asks for a directory's Go package for every cross-package component or
   record reference, and `gopkg.Resolve` parsed every handwritten `.go`
   file of that directory each time. `gopkg.Resolver` parses each
   directory once per run.
2. **Generation before the cache check.** A warm run generated every file
   and only then found the build cache current, so warm cost as much as
   cold. The cache is now checked first.
3. **Quadratic line-directive positions.** `settle` found each directive's
   line and column by counting from the start of the source: 110 of the
   250 ms of the application's largest document. A line-start index finds the same
   position by binary search.
4. **Sequential files.** Each file was prepared, then published in its
   own build-state transaction. Native generation now prepares files
   concurrently (largest first), generates both variants of a document in
   parallel, and publishes once.
5. **Quadratic cache checks.** Every cache hit resolved every output of the
   whole manifest. `buildstate.CacheChecker` validates ownership once per
   run.
6. **Garbage collection.** About 30% of the remaining CPU was GC.
   Generation raises `GOGC` to 400 unless `GOGC` is set.
7. **`ktml dev`** also validated every source one at a time to seed the
   hub (256 ms) and indexed the Explorer before generating (137 ms). The
   hub now validates the sources concurrently, and the Explorer starts
   alongside the generation.

Plugin backends are unchanged and still generate file by file, because
each plugin run holds the LSP proxy.

Generation does not start any plugin for the native backend, and gofmt
still formats every output: the confirming pass in `settle` is skipped
only when renumbering leaves gofmt's own output unchanged.

## Byte-identical output

The 180 files generated by the old binary were compared byte for byte
(`cmp`) with the output of every new build, cold and warm, through
`ktml generate` and `ktml dev`: no file differs.
`TestGenerateFilesContext_GIVENAWorkspace_WHENGeneratedTogether_THENMatchesGeneratingFileByFile`
checks the same property in the test suite.

## Regression gate

The gate test writes an application-shaped workspace: 6 packages of 8
documents with 4 components each, each component making 12 cross-package
calls, a Host Schema per package, and 1,500 functions of handwritten Go per
package (55 sources). It fails when cold generation takes more than 1 s or
warm more than 0.5 s, or when warm generation changes the build state.
Here it takes about 0.08 s cold and 0.02 to 0.04 s warm. The old code took
over 3.5 s for both on a lighter version of the workspace, and dropping
only the per-directory parse memo takes it to 1.13 s. The gate skips under
`-race` and `-short`.

```sh
go test ./cmd/ktml -run 'StaysWithinTheBudget' -v
go test ./cmd/ktml -run '^$' -bench GenerateFilesContext
```
